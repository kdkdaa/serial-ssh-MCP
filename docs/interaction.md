# 直接交互（0.3）

目标是像使用终端一样操作设备：Agent 给出输入，MCP 在已有会话中发送，设备产生输出，Agent 解释输出后继续。MCP 不检查 Linux、Windows 或 MCU 命令语法，不猜设备业务协议，也不自动纠错、重试或推断成功。

## 一次调用发送并收取输出

调用 `session_exchange`，例如下面两次是独立的工具调用，并使用相同 session_id：

```json
{"session_id":"已打开的会话ID","data":"cd /Project","newline":"cr"}
```

读取并判断第一条返回的内容后，再发送：

```json
{"session_id":"已打开的会话ID","data":"ls -la","newline":"cr"}
```

命令直接进入原来的终端，不额外创建子 Shell；只要目标终端自身支持持续目录状态，第二条就在切换后的目录执行。输入拼错时，设备的错误文本原样返回，Agent 判断并修正下一条。MCP 不识别 `cd`、不替换路径、不检查 `ls` 参数。

`data` 为文本时，按会话编码编码，并仅追加 `newline` 指定的结束符，默认 `none`。二进制输入指定 `data_format=hex`，例如 `data="a50100ff"`；`newline` 必须为 `none`，终止字节由 Agent 写入 hex。十六进制格式错误、未知会话、非法等待范围属于接口/传输参数错误；这与检查设备命令语法不同。

## 等待和续读

`wait_seconds` 默认 1 秒、范围 0～30 秒，是发送后本次收取的最长时间。收到 RX 后，如果连续 `quiet_seconds`（默认 0.1 秒、范围 0～5 秒）没有新 RX，可以提前返回。没有 RX 则等到收取期限。等待不发送额外探测命令，不中断设备，也不会自动续发输入。

**静默不是命令完成。** 回显后可能长时间才产生业务输出；长命令、交互问题、二进制响应及持续日志应由 Agent 结合内容判断。`quiet_seconds=0` 可在首批输出后立即返回；`wait_seconds=0` 只取当前已有的一页，不等待。

续读时省略 data，使用上次返回的 next_cursor：

```json
{"session_id":"已打开的会话ID","after":123,"wait_seconds":10}
```

这里 123 是示例值，必须换成实际游标。没有输入时不会发送任何字节，读操作可与后台任务并行。需要只发不等时使用原有 `session_send`；需要逐事件时间戳或 RX/TX 原始详情时使用 `session_read`。

发送时省略 `after`，从本次发送前的游标开始收取；纯读取省略 after 则从 0 开始，可能重复历史内容。有需要时可在发送时显式传入上一次游标，把两次调用间到达的日志一并取回。所有游标都由调用者持有，读取不消费其他读取者的数据。

## 返回内容

| 字段 | 含义 |
| --- | --- |
| `status` | received / no_data；也可能 busy、write_error、collection_error 或接口 error |
| `send` | 本次发送结果；纯读取时为 null。sent 仅表示传输接受字节 |
| `rx_text` / `rx_hex` | 同一批 RX 的增量解码文本与原始字节；包含回显、ANSI 和可能的后台日志 |
| `start_cursor` / `next_cursor` | 本次读取范围与续读位置 |
| `has_more` | 返回时当前录制里还有未读事件；可能包括非 RX 事件 |
| `may_receive_more` | 活连接仍可能继续产生数据，不保证一定有数据 |
| `stop_reason` | quiet / timeout / limit / session_ended，仅解释为何结束本次收取 |
| `session_state` / `error` | 会话状态与采集/传输异常；设备命令错误仍保留在 rx_text 中 |
| `completion` | 始终 unknown；直接通道不推断退出码或执行成功 |
| `duration_seconds` | 本次发送与收取在服务端的总耗时，不是纯设备执行时间 |

单次默认最多扫描 128 个事件，最多可设为 256；RX 文本 UTF-8 字节数与 hex 字符数合计限制为 64 KiB。到达上限后返回游标，原始录制继续进行。解码跨接收块的字符可能在下次返回才完整出现，以原始 hex 为准。

发送及其收取窗口期间持有会话操作锁，其他普通写入返回 busy；纯读取不占写锁。锁释放不代表设备已经结束命令，后续是否发送由 Agent 判断。显式中断/关闭仍可操作，但不自动执行。发送部分失败后不自动重发；如果已发送、后续收取发生异常，会保留发送状态、已收内容和游标。

## 适用范围与可选任务层

直接通道不绑定操作系统。Linux/Windows 终端必须已经通过支持的串口或 SSH 连接暴露；STM32 必须已有串口通信接口。MCP 不凭空提供 Windows 本地终端、JTAG、SWD 或芯片烧录能力。SSH PTY 合并 stdout/stderr，可能做终端转换；需要原始二进制链路时使用串口。

`task_*` 是可选的 POSIX 部署/断言执行层，仍有自己的计划格式、哈希和验证约束。它会使用独立 `sh -c` 与完成标记，不具备跨步骤 cd 状态；不要把它当作手工终端的默认入口。直接通道既不要求计划，也不执行这些检查。

直接通道减少的是客户端脚本、Shell 转义、计划构造与单次 send/read 往返。Agent 每次解释输出仍需要推理时间；大量已确定的固定步骤，任务层可能更快。0.3 已在 RK3566 上实测四次独立目录操作，服务端收发合计 532 毫秒（含每次 100 毫秒静默窗口），并完成只读网络查询；这不是其他设备、长任务或续读边界的性能保证。

## 宿主直接接入

正常路径是 `Agent → 已加载的 MCP 工具 → 设备`。项目已经提供 `.codex/config.toml` 和 `.mcp.json`；读取源码和临时启动 SDK 客户端是开发核验手段，不应成为每次设备操作的路径。

依据 [官方 MCP 配置说明](https://learn.chatgpt.com/docs/extend/mcp?surface=app)，项目配置需要信任项目；桌面客户端可以在 Settings → MCP servers 中管理服务，保存后选择 Restart，并通过 `/mcp` 查看连接。本项目配置指向已有虚拟环境与 launch.py，使用 STDIO，不需要外层 PowerShell。

只有宿主实际提供 `session_exchange` 等工具并能调用，才算直接接入成功。2026-11-10 检查时项目已被信任、配置存在，但当前聊天工具目录未暴露 Board Console，也没有可调用的 MCP 重载工具；因此不能声称本次已经解决宿主加载问题。
